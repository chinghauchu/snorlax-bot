# Snorlax-Bot v0.1 spec — chat layout + agent messaging

Product: Snorlax-Bot
Repo: https://github.com/chinghauchu/snorlax-bot
Audience: Backend, Frontend (macOS Tauri), iOS
Status: **locked 2026-08-25**. Engineering may build from this. CEO confirmed the four defaults. Backend's hop 0→1 / one-mention cut is **rejected**.

**v0.1.1 (CEO 2026-08-25, after Chinghau's test):** 1:1 transcripts are isolated. Agent–agent traffic displays in the seeded `Snorlax-Bot` group channel, not in 1:1s. This overrides the v0.1 "DM-in-1:1s / involve bubble" surface. Hop caps and runtime-routed mentions are unchanged. See §2, §4, and §7.

**v0.2 (CEO 2026-08-25):** Collaboration fluency. A user `@chip` in A's 1:1, or A DMing B, opens a **channel thread** under a LEFT `kind=handoff` card authored as A. Pack B wakes with `{ originating, userAsk, brief, mentionedIds }` (not a quote). A's 1:1 stays user + A + a jump chip when the user caused the handoff. Isolation is unchanged. See §8.

**v0.3 (CEO 2026-08-25):** Agent identity + info pane. Header click (desktop also Cmd+Shift+I) opens a 320px overlay / iOS sheet. `kind=agent` is editable identity; `kind=channel` is a read-only member list. Seed DELETE is 204 with no auto-reseed. Seeded channel DELETE stays 409. Isolation is unchanged. See §9.

**v0.4 (CEO 2026-08-26, after Chinghau's 1:1 @mention screenshot):** Collaboration report-back + extra user-created channels. 1:1 @involves log on seed `snorlax-bot-group` only. B does the task in the channel thread (no ACK classifier). A reports each result in A's 1:1 as that peer lands (not a hop). Isolation is unchanged: B does not appear as B in A's 1:1. Users can create additional `kind=channel` rows and PATCH their members. See §10.

v0 still stands: local inference on DGX Spark, macOS desktop + thin iOS companion, no Cursor login. This spec adds two features on top of the chat loop.

## Problem

1. Chat reads as a log. Grok Bot (and iMessage) put the user on the right and everyone else on the left. Desktop and iOS must match.
2. Chinghau created a second agent and expected Grok-Bot-like teammate messaging. Isolated 1:1 transcripts mean agents cannot see or reach each other.

## Not in v0.1

No tools, MCP, connectors, skills, sandbox/box, computer-use, routines, or question widgets. No copying a private 1:1 into a channel unless the user asked to tell the room (an `@` mention is that ask). One seeded channel plus extra user-created channels (v0.4).

## 1. Chat layout (desktop + iOS)

- User messages: RIGHT. Distinct user fill. No avatar required on the right.
- Agent messages: LEFT, with that agent's avatar + display name on the first bubble of a streak.
- Consecutive bubbles from the same speaker stack. A speaker change starts a new streak.
- Streaming tokens render in-place in the left bubble.
- Do not show raw runtime cues (`[agent]`, `[Group chat:]`, `[routine]`) to the user.
- Alignment is a client rule: `author.kind == user` → right; anything else → left.
- A 1:1 never shows another agent's bubble, an involve line, or muted `to B` / `from A` chrome.

## 2. Surfaces

Two surfaces, both required.

### Group channel (shared transcript)

- Seed one channel named `Snorlax-Bot` (id `snorlax-bot-group`, kind `channel`). Every agent is a member. New agents auto-join it.
- The seed 1:1 is a **distinct** resource: id `snorlax-bot`, name **Snorlax**, title Assistant, kind `agent`. Never reuse `snorlax-bot` as the channel transcript.
- Sidebar lists both as normal rows. The channel row shows a muted “Channel” subtitle from `kind` (12px / 12pt), not by guessing id. Never two rows named “Snorlax-Bot”. Do not show ids in chrome.
- One shared channel transcript. User can read and send.
- User messages: right. Agent posts: left, identified.
- Posts are async. Nobody waits for a reply. Unmentioned members stay silent unless they have something material to add.
- **This is the display surface for agent–agent traffic.** If A talks to B, it appears here, not in A's 1:1 or B's 1:1.

### Agent 1:1 (user ↔ that agent only)

- A 1:1 with agent A (including Snorlax at `snorlax-bot`) shows **only** the user (right) and A (left).
- No other agent's bubbles. No involve line `{User} mentioned you in {A}`. No muted `to B` / `from A` DM chrome.
- GET/list and SSE must not paint peer messages into a 1:1. Filter: `senderId` is `user` or that agent. The channel is shared and is not filtered that way.

## 3. `@` syntax

- Mentions resolve by agent id from the typeahead chip. The composer sends `mentions: [id, ...]`.
- Unresolved `@text` (typed but not picked from typeahead) is NOT a mention. It stays plain text. Do not 422 the send just because someone typed `@foo`.
- **422 only for an unknown chip id** (and `@everyone` chip in a 1:1). Unknown/ambiguous `@text` in the body is omitted.
- No display-name prefix matching on user sends. Exact `@DisplayName` in the body may still route (same as a resolved chip).
- Multiple mentions are allowed on one send, bounded by the hop / peer-send caps in section 5. A one-mention-per-send cap is rejected.
- `@everyone` is valid only in a group channel (all members are addressed). Invalid as a chip in 1:1. Typed `@everyone` in a 1:1 is plain text.
- **Group channel:** the message is stored in that channel only. Mentioned agents are addressed and should reply. Unmentioned agents stay silent by default.
- **1:1 with agent A:** `@B …` stays in A's transcript as the user's bubble (right). A replies in that 1:1. B does **not** appear in A's 1:1. B does **not** get an involve bubble in B's 1:1. B is addressed in a **handoff thread** on the seeded channel (v0.2).
- Agent-authored `@Name` notifies that member the same way a user mention does. If that mention originates in a 1:1, the peer traffic still lands in the channel.
- Mentions are highlighted in the bubble. Composer offers `@` autocomplete of agent display names (desktop + iOS). Inserting a chip keeps a stable caret after the chip; the chip stays a chip.

## 4. What appears in which transcript

- User talks to A in 1:1 → only A's 1:1. User right, A left.
- User `@B` in A's 1:1 → A's 1:1 keeps the user-right chip (plus a jump line when a handoff was created) and A's reply. B does not appear in A's or B's 1:1. The seeded channel gets a LEFT `kind=handoff` root authored as A (`from {A}` + `userAsk`, brief collapsed as Context) and a flat thread of replies. Not a user-right copy in the channel.
- A talks to B (agent-authored `@B` or a routed mention) → the same channel thread, not A's 1:1 or B's 1:1. No jump chip unless the user caused the handoff.
- Anyone posts in the group channel → that channel transcript. Mentioned agents wake. 1:1s are unchanged unless the user is also chatting there separately.

Privacy: a 1:1 with the user is private. Do not relay it into a channel or to another agent unless the user `@` mentioned them or explicitly asked to tell them.

## 5. Loop / hop limits

Locked. Do not implement hop 0→1-only.

- User → current agent is hop 0.
- Max hop depth: 3 (A→B→C→D ok; D→E dropped).
- Max peer sends (DMs + channel posts) per originating user turn: 4.
- Same-edge cap: A→B→A once per turn; a second A→B in that turn is dropped.
- Dropped messages are silent in the UI. Runtime logs them. Sender is not prompted to retry.
- Delivery is always async. Recipients never block the sender.

These caps are unchanged in v0.1.1. Only the **display surface** for peer traffic changed: channel, not 1:1s.

## 6. Acceptance checks

Desktop (macOS) and iOS must each pass:

- User bubble is right; the current agent's bubble is left with name + avatar.
- In the seeded channel, a second agent's posts are left and labeled as them, never as the user.
- From agent A's 1:1, user sends `@B hello`. A's 1:1 shows the user (right), a jump line “Also in Snorlax-Bot” when `handoff` is set, and A (left) only. B's 1:1 is empty of that turn. The channel timeline shows a compact handoff row; the thread has A's card and B's reply.
- Scrolling a long 1:1 or channel transcript does not scroll the 256px agent list. Only the transcript pane scrolls.
- Right-click (desktop) or swipe/context (iOS) deletes a **kind=agent** row after confirm `Delete {name}? This removes the agent and its chat.` That includes seed `snorlax-bot` (DELETE 204, no auto-reseed). Seeded channel `snorlax-bot-group` hides Delete; API DELETE returns 409. Delete is not in the info pane.
- `@` autocomplete lists agent names. Picking a chip keeps the caret after the chip. Unresolved `@text` stays plain text; send does not error.
- Streaming tokens stay left-aligned.
- Fourth hop is dropped (debug/test hook is enough).
- Two mentions on one user send both deliver (inside the peer-send cap).

iOS-only: agent list includes the seeded channel; user can read and send in 1:1 and in that channel over LAN.

## 7. Locked decisions (2026-08-25)

1. User `@Name` in a 1:1 is runtime-routed to that agent (not "model must remember to send").
2. One seeded `Snorlax-Bot` channel; all agents auto-join it. Extra user-created channels are v0.4 (`POST /v1/agents` with `kind=channel`).
3. Hop limit 3, max 4 peer sends per user turn, same-edge once. Hop 0→1 / one-mention-per-send is rejected.
4. **v0.1.1:** Agent–agent traffic displays in a channel, not in the two 1:1 transcripts. 1:1 isolation overrides the earlier "DM-in-1:1s / involve bubble" rule. Seed `snorlax-bot` is the Snorlax 1:1 only. v0.4 1:1 @involves always log on seed `snorlax-bot-group`; extra channels are a separate create flow.
5. 422 only for an unknown typeahead chip id (and `@everyone` chip outside the group).
6. Roster names: seed 1:1 is **Snorlax**; channel is **Snorlax-Bot**. Clients show muted “Channel” from `kind`. Never two rows named Snorlax-Bot. Do not show ids in chrome.
7. Collaboration fluency is **v0.2** (handoff pack / channel thread / jump chip). v0.1.1 isolation stays.
8. **v0.3:** Header info pane. kind=agent is editable identity; kind=channel is a read-only member list. Seed DELETE is 204 and is not auto-reseeded. Seeded channel DELETE stays 409. User-created channel DELETE is 204 (v0.4).
9. **v0.4:** Report-back into A's 1:1 (not a hop; report as each peer lands). Extra channels with member editor. Isolation unchanged.

## 8. v0.2 — collaboration handoff (locked)

When a handoff happens (user `@chip` in A's 1:1, or A DMs B):

- A still answers in the 1:1 (user + A). Looping B does not suppress that.
- Pack B wakes with (not a quote): `{ originating: { id, name, title }, userAsk, brief, mentionedIds }`.
- `brief` = last 8 messages of that 1:1, user+A only, cap 2k chars, drop oldest.
- Agent DM: `userAsk` = A's text; `brief` = last 8 of A's 1:1.

### Channel thread

On `snorlax-bot-group`. Root is a LEFT handoff card authored as A (muted “from {A}” + `user_ask`; brief collapsed as Context). Flat thread under that root; later hops stay here. B/A post LEFT; user in the thread is RIGHT. Unread on the channel row.

GET channel messages must **not** dump thread replies onto the timeline. Timeline = handoff roots (and other unreplied-to roots). `?threadId=` (or `replyTo`) returns that thread.

### Jump chip (only when the USER caused the handoff)

Muted 12px / 12pt system line under the user-right bubble that has the `@chip`. Copy “Also in {channel name}” (accent on the name; seed is Snorlax-Bot). Not a bubble, no avatar, no B text. Whole line tappable → opens the channel at that thread. No `handoff` field → no chip. Second `@B` in that 1:1: reuse the same thread, new jump line under that bubble. Hop/cap silent drop → no `handoff` field, no chip.

Where: A's 1:1 = user, A, jump chip. B's 1:1 unchanged. Peer lives in the thread.

### API (additive)

Keep `senderId` / `hop` / `mentions`. Add `replyTo` on channel msgs. Originating user message gets `handoff: { channelId, threadId }` (no fake speaker). `kind: handoff` on the channel root. 422 still unknown chip id.

### Chrome

Channel timeline: one compact LEFT row per handoff: A's 20px avatar + name, muted “from {A}”, one-line `user_ask`, muted “N replies”. Tap opens the thread. Thread: back to timeline; root LEFT card (A's avatar + name, muted from A, `user_ask`, collapsed Context). Replies under it, same L/R. Unread = 6px accent dot on the channel roster row. Desktop first, iOS match.

Not in v0.2: widgets, box, tools, MCP, skills, extra channels. Do not reopen 1:1 isolation.

## 9. v0.3 — agent identity + info pane (locked)

Header click (whole header row: 24px / 24pt avatar + name) opens an info pane. Desktop also **Cmd+Shift+I**. Close is **X** on the pane. Opening the pane does not change the 1:1 transcript. Desktop: **320px overlay on the chat**, not a third column. iOS: sheet.

**Agent vs channel are different panes.** Never treat `snorlax-bot-group` as an agent profile.

### Agent pane (`kind=agent`, including seed Snorlax)

72px / 72pt avatar (initials from name if empty), 16px / 16pt name, 13px / 13pt muted title + description. Gear beside X edits those four. Save is `PATCH { name, title, description, avatar }` to `/v1/agents/{id}`. Id is not editable. Empty avatar → initials. Avatar is a PATCH string or null (data URI or persisted `/v1/images/{id}`); no second upload API.

CEO override: seed `snorlax-bot` DELETE is **204**, gone from GET, no auto-reseed. Empty roster is fine. Channel `snorlax-bot-group` DELETE stays **409**. Delete is sidebar right-click / iOS swipe, **not** in the info pane. Seed row gets the same Delete as user-created agents. After seed delete, if the roster is only the channel, select **Snorlax-Bot** — do not fake a seed. Seed identity PATCH is allowed. User-created: PATCH + DELETE as today.

### Channel pane (`kind=channel`)

**Seed `snorlax-bot-group`:** Read-only. Display name + muted Channel + member list from `memberIds` (avatar + name + title each). No gear, no PATCH name, no avatar editor. 44px / 44pt member rows, not tappable in this slice. All agents auto-join; DELETE 409.

**User-created channel:** Same member rows. Gear beside X edits `name` + `memberIds` (`PATCH { name, memberIds }`). Seed pane stays read-only.

Header keeps showing live name/title/avatar after PATCH. Roster updates too. 1:1 is still user+A only.

Not in v0.3: computer preview (no placeholder), routines list, connector/Channels row, per-agent notifications, shape/color beyond avatar, create-agent wizard, sidebar sections.

## 10. v0.4 — report-back + extra channels (locked)

Keep isolation: GET/transcript of A's 1:1 is still only user + A. B does not appear as B. No involve bubble, no “from Test” speaker in the 1:1. Jump chip “Also in {channel}” may remain as an optional inspect link under the user's @ message only; it is **not** required to get the answer.

### Report-back

1. User `@chip` B in A's 1:1 (typeahead id). Runtime wakes B with the existing handoff pack (`originating`, `userAsk`, brief last 8, `mentionedIds`) in a **seed** `snorlax-bot-group` thread. Extra channels are a separate create flow; 1:1 involves never open a new channel per mention and never log on a user-picked extra channel.
2. B's system/wake: you were asked to **do** the task. First reply is the work product. Do not acknowledge that you can. Do not ping-pong. Prompt/task only — **no ACK classifier** in code (do not detect “I can help”). FYI with no ask → stay silent (`looks_like_ask` is FYI silence, not an ACK retry).
3. When B's channel-thread turn completes (`message.done`) **or B is hop/cap dropped**, enqueue a generation for A on A's 1:1. This is **not** a peer send. It does **not** increment hop or spend hop budget. Hop caps only apply to A2A/channel peer sends.
4. Prompt to A (not a Message field): `{ result, from: { id, name, title }, threadId, userAsk }`. Hop-drop: `result` is a miss so A still tells the user B wasn't reached.
5. Persist a normal assistant Message in A's 1:1: `role=assistant`, `senderId=A`, `senderName`/`avatar`=A, **no mentions of B**, **no `from` field on the Message**. Isolation: never write B into A's 1:1. B's 1:1 stays empty.
6. Multiple `@chips`: fire A's report as **each** B lands (don't wait-for-all). Serialize A's report-back gens on that 1:1 so tokens don't interleave (insert the report-back as the next job after that peer).
7. Hold the originating 1:1 POST SSE open until every mentioned B has done or been dropped **and** A has reported for each. Extra `message.delta` / `message.done` on the **same** stream. No new SSE event type.
8. Chrome: report-back is another of A's **LEFT** bubbles in the 1:1 (20px avatar+name, no from B). Jump chip only under the user's @ message. Hop-drop is still A's LEFT bubble, no system chrome. Do not duplicate `from {Name}:` inside bubble body.
9. Channel thread remains the A2A log. Timeline = handoff roots; `?threadId=` = thread. `@mention` inside an extra channel stays in **that** channel's thread.

### Extra channels

- Seeded `snorlax-bot-group` / Snorlax-Bot stays. Auto-joins all agents. PATCH 409. DELETE 409. No member editor on seed this slice.
- User can create additional channels: `POST /v1/agents` `{ name, kind: "channel", memberIds }` → 201. Omit kind → still create agent. `memberIds` are agent ids only; 422 unknown id / channel id in the list / missing name. Omitted memberIds snapshot every current agent. New agents auto-join seed only, not extras.
- User-created channel PATCH `{ name, memberIds }` → 200 (add/remove members). DELETE 204. Agent DELETE (including seed `snorlax-bot`) stays 204 from v0.3. No new upload route.
- Desktop + iOS: `+` opens a **160px / 160pt** menu: New agent / New channel. New channel is a **320px overlay / iOS sheet**: name + member picker (44px rows, 28px avatar, checkbox, agents only). User-created channel pane has a gear; seed pane stays read-only. Delete is sidebar/swipe, hidden on seed channel.

Not in v0.4: widgets, box, tools, MCP, skills, vision.
